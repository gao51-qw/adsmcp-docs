A read runs right away. A change — create, pause, enable, budget, bid, status, or delete — never runs on the call. It becomes a **pending action**, and nothing happens in your ad account until a person approves it.

## Where to approve

Open [Ad Ops → Approvals](https://adsmcp.si/dashboard/approvals). Each pending action shows the tool, the platform, the account, the arguments and a risk level.

- **Approve & Execute** runs the change with the stored arguments.
- **Reject** discards it. You can add a reason and save it as a [Knowledge Studio](/knowledge-studio) draft so the agent learns from it.

Only a person can approve. This is true whatever the tool arguments say: `execution_mode` and similar fields never skip the queue.

## The approval link

Every reply that stages a change carries an `approval_url` (`https://adsmcp.si/dashboard/approvals?id=...`) and a short message for your AI to show you. Open the link and the approvals page shows that change, highlighted. You can also select several pending actions and approve them in one step.

## Approving in your AI client

Some AI clients can show a confirm dialog and run the change when you click Approve there. The change runs through the same path as a dashboard approval, including the spend cap. Decline rejects the change. Closing the dialog leaves it pending, and you can still approve it from the link.

The dialog appears only when all of these are true:

- The client uses protocol version 2026-07-28 and supports form confirmations.
- You connected the client with OAuth, not an API key.
- The client is on ADSMCP's list of allowed clients. That list is empty for now, so no client shows the dialog yet and every change is approved on the dashboard. This page lists clients when they do.
- The setting **Allow approving changes in the AI client** is on. It is on by default; turn it off in [Settings](/settings) under Preferences.
- The tool is not a delete (including deletes by status) and not `create_chatgpt_conversions_api_key`. These can only be approved on the dashboard.
- The change has a readable before and after, or it is a create that will be staged paused. Otherwise you get the link only.

Every decision is recorded with the channel it came from: `dashboard` or `client_confirm`. See [Safety model](/safety#what-the-confirm-dialog-does-and-does-not-stop) for what the dialog does and does not guard against.

## In a team

In a [team](/teams), the owner and admins can approve by default; the owner can limit approval to the owner, or let members approve their own changes. An approver can approve a change staged by any member, but it runs as its author: the author's connection, active accounts and spend cap. The author can always reject their own change. A change whose result contains a one-time secret (`create_chatgpt_conversions_api_key`) can only be approved by its author. An approval in the AI client's dialog is checked against the same team approval roles as a dashboard approval. Every decision is recorded with who made it and their role.

## What an AI client can do

| Tool | What it does over MCP / REST |
| --- | --- |
| `list_pending_actions` | List your pending actions (view only). |
| `manage_action` | `decision: "view"` shows one action; `decision: "reject"` rejects it. `approve` is refused with `approval_requires_dashboard`: the AI model cannot approve. |
| `list_execution_queue` | List approved actions and their run status (view only). |
| `list_dead_letter_queue` | List actions whose run failed and was set aside. |
| `resolve_dead_letter_action` | Close a dead-letter item as `resolved` or `rolled_back`. It never runs or re-queues it. |
| `get_action_audit` | Read the history of proposals, approvals and runs. |
| `execute_queued_action`, `retry_queued_action`, `resume_workflow_after_approval` | Always refused with `approval_requires_dashboard`. |

## What happens when you approve

1. The stored change runs once, exactly as approved.
2. Creates are made paused or as drafts, so they cannot spend yet.
3. Budget changes and enables are checked against your [spend cap](/safety#spend-cap) first. Over the cap, or if a budget cannot be read, the change is refused and nothing is sent to the platform.
4. Deletes were only staged if the call carried `confirm_delete: true`; once approved they cannot be undone.
5. If the platform rejects the change, the failure is shown on the item. Nothing retries automatically. Fix the cause and stage a corrected change, which needs a new approval.

You can follow your approved changes on the [Execution Queue](https://adsmcp.si/dashboard/execution-queue) page, which shows each one's run status, last error and audit trail, including changes that failed when they ran. To investigate a failure, call `get_recent_errors`, `get_request_trace` or `search_service_events`. They return only your own events. Admins see every user's events and also have the [Diagnostics](https://adsmcp.si/dashboard/diagnostics) page.

## Monitors, rules and schedules

`test_monitor`, `test_automation_rule` and `optimize_budget` can stage pending actions too. They land in the same queue and wait for the same approval. See [Alerts](/alerts) and [Automation](/automation).
